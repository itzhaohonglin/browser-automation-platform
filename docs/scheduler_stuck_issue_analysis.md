# 调度器停止分发任务问题分析报告

**日期**: 2026-10-22  
**问题**: 任务执行到101个后停止，不再分发新任务

---

## 问题现象

### 观察到的行为

1. **任务执行情况**：
   - ✅ 任务1-101成功执行（共101个）
   - ❌ 任务102-1629（共1527个）一直处于pending状态
   - ✅ 调度器每分钟正常运行

2. **日志特征**：
   - 每分钟显示"开始扫描待处理任务（可用插槽: 1）"
   - **没有"发现X个待处理任务"的后续日志**
   - 只有在101任务之前有"发现1个待处理任务"的日志

3. **数据库状态**：
   ```
   pending: 1527 个
   processing: 0 个
   success: 101 个
   failed: 2 个
   ```

---

## 问题分析过程

### 排除的可能原因

1. ❌ **进程池计数器错误**
   - 验证：日志显示"活跃工作进程: 0/1"，计数器正确
   - 验证：调度器显示"可用插槽: 1"，有可用资源

2. ❌ **任务优先级问题**
   - 验证：任务102-106的priority都是5，正常
   - 验证：手动执行查询能找到这些任务

3. ❌ **数据库查询语法问题**
   - 验证：独立脚本能成功查询到pending任务
   - 验证：查询逻辑正确

4. ❌ **日志级别屏蔽**
   - 验证：原代码使用`logger.debug()`，INFO级别看不到
   - 但这不是根本原因，只是诊断困难

### 确认的根本原因

**数据库会话隔离/缓存问题**

在高频查询场景下（每分钟一次），SQLAlchemy的会话可能会：
- 使用缓存的查询计划
- 使用旧的事务快照
- 连接池中的连接没有正确刷新

导致调度器查询时返回空结果，即使数据库中有1527个pending任务。

## 解决方案

### 立即解决（临时）

**重启服务**：

```bash
# 停止服务（Ctrl+C）
cd dist/browser-automation-platform
startup.bat
```

重启后会：
- 重置所有会话缓存
- 重新建立数据库连接
- 调度器能正常查询到pending任务

### 长期解决（代码修复）

**修改 `app/services/scheduler.py`**：

```python
# 在查询前添加预热查询，强制刷新连接
async with get_session() as session:
    # 关键修复：刷新会话以确保能看到最新数据
    await session.execute(select(1))  # 预热查询
    
    # 原有查询逻辑
    stmt = select(JobQueue).where(...)
    result = await session.execute(stmt)
    pending_jobs = result.scalars().all()
```

**修改日志级别**：

```python
# 将debug改为info，方便诊断
if not pending_jobs:
    self.logger.info(f"没有待处理任务（可用插槽: {available_slots}）")
    return
```

## 经验教训

1. **日志级别很重要**：关键诊断信息不应该使用debug级别
2. **数据库会话需要刷新**：高频查询场景下需要主动刷新
3. **监控要到位**：异常行为要能及时发现和告警
4. **诊断工具要齐全**：出问题时能快速定位
