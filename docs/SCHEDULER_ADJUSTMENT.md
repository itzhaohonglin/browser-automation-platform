## 📋 当前调度配置

### 1. 失败任务重试
```python
RETRY_INTERVAL_MINUTES = 30      # 每 30 分钟扫描一次
FIRST_RUN_DELAY_MINUTES = 1      # 启动后 1 分钟首次执行
MAX_RETRY_COUNT = 3              # 最多重试 3 次
```

**任务**: 扫描 `status='failed'` 且 `retry_count < 3` 的任务，重置为 `pending` 状态

**执行频率**: 每 **30 分钟**一次 ✅

### 2. 待处理任务分发
```python
trigger=IntervalTrigger(seconds=10)  # 每 10 秒
next_run_time=启动后 5 秒
```

**任务**: 扫描 `status='pending'` 的任务，分发到进程池执行

**执行频率**: 每 **10 秒**一次（保持不变）

### 3. 告警规则评估
```python
ALERT_EVAL_INTERVAL_MINUTES = 5  # 每 5 分钟
ALERT_FIRST_RUN_DELAY_MINUTES = 2  # 启动后 2 分钟首次执行
```

**任务**: 评估告警规则（失败率、队列积压等）

**执行频率**: 每 **5 分钟**一次（保持不变）

## ⏰ 调度时间轴

```
服务启动后:
├─ 5 秒    → 首次分发待处理任务
├─ 10 秒   → 第2次分发
├─ 20 秒   → 第3次分发
├─ 1 分钟  → 首次扫描失败任务（重试）
├─ 2 分钟  → 首次评估告警规则
├─ 31 分钟 → 第2次扫描失败任务（重试）✨
├─ 61 分钟 → 第3次扫描失败任务（重试）✨
└─ ...持续运行

持续执行:
├─ 每 10 秒  → 分发待处理任务（高频）
├─ 每 5 分钟  → 评估告警规则（中频）
└─ 每 30 分钟 → 重试失败任务（低频）✨ 已修改
```

---

## 💡 为什么修改为 30 分钟？

### 优势
1. ✅ **降低服务器负载** - 减少数据库查询频率
2. ✅ **避免频繁重试** - 给失败任务更多冷却时间
3. ✅ **适合目标网站限流** - 减少被封禁的风险
4. ✅ **节省系统资源** - 降低 CPU 和内存占用

### 适用场景
- ✅ 目标网站有访问频率限制
- ✅ 任务不需要立即重试
- ✅ 生产环境稳定运行
- ✅ 大量任务（如本次的 1625 个）

### 不适用场景
- ⚠️ 需要快速重试的场景（如网络抖动）
- ⚠️ 开发调试阶段

## ⚠️ 注意事项

1. **修改后需要重启服务**
   ```bash
   # 停止当前服务（Ctrl+C）
   # 重新启动
   python -m app.main
   ```

2. **已在运行的任务不受影响**
   - 只影响失败任务的重试间隔
   - 待处理任务仍然每 10 秒分发

3. **失败任务的重试时机**
   - 第 1 次失败：30 分钟后重试
   - 第 2 次失败：再等 30 分钟重试
   - 第 3 次失败：再等 30 分钟重试
   - 第 4 次失败：不再重试（达到 MAX_RETRY_COUNT）

4. **监控建议**
   - 定期查看看板统计
   - 关注失败任务的错误日志
   - 必要时手动重置失败任务状态
