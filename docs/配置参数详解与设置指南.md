## MAX_WORKERS - 并发控制

### 🎯 作用

**控制同时执行的任务数量**（并发度），即进程池的工作进程数。

```
┌─────────────────────────────────────┐
│         进程池管理器                 │
│  ┌──────┐ ┌──────┐ ┌──────┐        │
│  │ 工作1 │ │ 工作2 │ │ 工作3 │  ← MAX_WORKERS=3
│  └──────┘ └──────┘ └──────┘        │
│                                     │
│  任务队列: [任务4, 任务5, 任务6...]  │
└─────────────────────────────────────┘
```

### 💡 工作原理

```python
# 假设 MAX_WORKERS=3
# 同一时刻最多有 3 个浏览器实例在运行
进程1: 正在采集任务 #101 → 浏览器A
进程2: 正在采集任务 #102 → 浏览器B  
进程3: 正在采集任务 #103 → 浏览器C
等待中: 任务 #104, #105, #106...
```

**执行流程**：
1. 调度器每 30 分钟扫描一次 `pending` 任务
2. 计算可用插槽 = `MAX_WORKERS - 当前运行任务数`
3. 提交任务到进程池（不超过可用插槽）
4. 任务完成后释放插槽，下一批任务自动进入

### 📊 影响因素

#### 1. 机器资源
```
每个工作进程的资源消耗：
- CPU: 10-20%（单核）
- 内存: 200-500MB（由 WORKER_MEMORY_LIMIT_MB 控制）
- 带宽: 取决于页面大小，通常 1-5 Mbps
```

#### 2. 目标网站压力
```
并发过高的风险：
- 触发网站反爬机制（IP 封禁、验证码）
- 请求被限流（429 Too Many Requests）
- 数据采集失败率上升
```

### ⚙️ 设置建议

#### 📏 计算公式

```
MAX_WORKERS = min(
    机器可用核心数 / 2,
    (目标站点限流阈值 / 单任务耗时) × 安全系数
)
```

#### 🎚️ 推荐配置

| 机器配置 | CPU | 内存 | 推荐值 | 说明 |
|---------|-----|------|--------|------|
| 低配 | 4核 | 8GB | **2-3** | 保守配置，稳定优先 |
| 中配 | 8核 | 16GB | **3-5** | 平衡配置，适合大多数场景 |
| 高配 | 16核 | 32GB | **5-10** | 高并发配置，需配合限流 |
| 超高配 | 32核+ | 64GB+ | **10-20** | 大规模采集，必须启用限流 |

#### ⚠️ 注意事项

```bash
# ❌ 不推荐
MAX_WORKERS=1   # 太保守，效率低
MAX_WORKERS=20  # 未启用限流时风险极高

# ✅ 推荐
MAX_WORKERS=3   # 默认值，适合大多数场景
MAX_WORKERS=5   # 中等规模采集（需配合限流）
```

## 限流配置 - 访问频率控制

### 🎯 作用

**控制单位时间内执行的任务数量**，防止对目标网站造成过大压力，避免被封禁。

### 💡 工作原理

#### 核心概念：时间窗口滑动

```
时间轴 (RATE_LIMIT_WINDOW_MINUTES=60):
│←─────────────── 60分钟 ──────────────→│
│                                       │
│ 任务1  任务2  任务3  ...  任务100      │ ← RATE_LIMIT_MAX_TASKS=100
│                                       │
└───────────────────────────────────────┘
         ↓ 时间推进，窗口滑动
         │←─────────────── 60分钟 ──────────────→│
         │                                       │
         │   任务2  任务3  ...  任务100  任务101  │
         │                                       │
         └───────────────────────────────────────┘
```

#### 限流检查流程

```python
任务分发前检查：
1. 获取当前时间窗口内已执行任务数
2. 判断: 已执行任务数 < RATE_LIMIT_MAX_TASKS ?
   ├─ 是 → 允许执行，记录时间戳
   └─ 否 → 跳过任务，等待下次检查

窗口滑动：
- 过期任务自动移出统计（超过窗口时间）
- 只统计窗口内的任务数
```

### 📊 两个关键参数

#### 1. RATE_LIMIT_WINDOW_MINUTES（时间窗口）

**定义**: 限流统计的时间范围（分钟）

```bash
# 示例
RATE_LIMIT_WINDOW_MINUTES=60   # 统计过去 60 分钟内的任务
RATE_LIMIT_WINDOW_MINUTES=120  # 统计过去 120 分钟内的任务
```

**作用**：
- 时间窗口越短 → 限流越严格（突发流量控制）
- 时间窗口越长 → 限流越平滑（长期流量控制）

#### 2. RATE_LIMIT_MAX_TASKS（任务上限）

**定义**: 时间窗口内允许执行的最大任务数

```bash
# 示例
RATE_LIMIT_MAX_TASKS=50   # 窗口内最多 50 个任务
RATE_LIMIT_MAX_TASKS=100  # 窗口内最多 100 个任务
RATE_LIMIT_MAX_TASKS=300  # 窗口内最多 300 个任务
```

**作用**：
- 任务上限越低 → 访问频率越低（更安全）
- 任务上限越高 → 访问频率越高（效率优先）

### ⚙️ 设置建议

#### 📏 计算公式

```
RATE_LIMIT_MAX_TASKS = 目标网站限制 × 安全系数（0.6-0.8）
RATE_LIMIT_WINDOW_MINUTES = 目标网站限制时间窗口
```

#### 🎚️ 推荐配置

##### 场景 1: 严格限流（高风险网站）
```bash
RATE_LIMIT_ENABLED=true
RATE_LIMIT_WINDOW_MINUTES=60     # 1小时窗口
RATE_LIMIT_MAX_TASKS=50          # 每小时 50 个任务
# 平均: 50任务/小时 = 1.2分钟/任务 = 每72秒一个任务
```

**适用场景**：
- 目标网站有明确的访问频率限制
- 网站反爬机制较强（如银行、政府网站）
- IP 被封禁风险高

##### 场景 2: 中等限流（平衡型）
```bash
RATE_LIMIT_ENABLED=true
RATE_LIMIT_WINDOW_MINUTES=60     # 1小时窗口
RATE_LIMIT_MAX_TASKS=100         # 每小时 100 个任务
# 平均: 100任务/小时 = 0.6分钟/任务 = 每36秒一个任务
```

**适用场景**：
- 电商网站、社交平台等常规网站
- 中等规模采集（1000-10000 条数据）
- 需要平衡效率和安全

##### 场景 3: 宽松限流（低风险网站）
```bash
RATE_LIMIT_ENABLED=true
RATE_LIMIT_WINDOW_MINUTES=60     # 1小时窗口
RATE_LIMIT_MAX_TASKS=300         # 每小时 300 个任务
# 平均: 300任务/小时 = 0.2分钟/任务 = 每12秒一个任务
```

**适用场景**：
- 公开数据网站（如政府公开数据）
- 网站无明确限流措施
- 大规模采集但时间要求不紧急

##### 场景 4: 不限流（内部测试）
```bash
RATE_LIMIT_ENABLED=false
# 其他限流参数无效
```

**适用场景**：
- 本地测试环境
- 内部系统（无反爬限制）
- 已有其他限流机制

## 两者关系与协同配置

### 🔗 区别与联系

| 维度 | MAX_WORKERS | 限流配置 |
|------|-------------|----------|
| **控制对象** | 并发任务数（同时运行） | 时间窗口内总任务数（累计） |
| **控制粒度** | 瞬时并发 | 长期频率 |
| **主要目的** | 资源管理（CPU/内存） | 反爬虫/网站保护 |
| **生效时机** | 任务分发时 | 任务执行前 |
| **失控后果** | 服务器资源耗尽 | IP 被封禁 |

### 📐 协同工作示意图

```
时间轴 (60分钟窗口):
0分    10分   20分   30分   40分   50分   60分
│──────│──────│──────│──────│──────│──────│
│ ███  │ ███  │ ███  │ ███  │ ███  │      │  ← 每 10 分钟执行一批
│      │      │      │      │      │      │
总执行: 50 个任务 < RATE_LIMIT_MAX_TASKS(100) ✅

每批并发: 3 个任务 = MAX_WORKERS(3) ✅

说明:
- MAX_WORKERS=3: 每批最多 3 个任务同时运行
- RATE_LIMIT_MAX_TASKS=100: 60分钟内累计不超过 100 个任务
- 两个限制同时生效，取更严格的限制
```

### ⚖️ 配合原则

#### 原则 1: 限流优先
```
限流是对外承诺，MAX_WORKERS 是内部优化
→ 先确定限流参数，再调整并发数
```

#### 原则 2: 并发不应超过限流承受能力
```bash
# ❌ 错误配置
MAX_WORKERS=10                    # 10 个任务同时执行
RATE_LIMIT_MAX_TASKS=50           # 60 分钟内最多 50 个任务
RATE_LIMIT_WINDOW_MINUTES=60
# 问题: 如果 10 个任务同时完成，立即提交下一批 10 个
#      可能在短时间内用完配额，导致长时间空闲

# ✅ 正确配置
MAX_WORKERS=3                     # 3 个任务同时执行
RATE_LIMIT_MAX_TASKS=50           # 60 分钟内最多 50 个任务
RATE_LIMIT_WINDOW_MINUTES=60
# 优势: 任务均匀分布在 60 分钟内，充分利用配额
```

#### 原则 3: 考虑任务耗时
```
平均任务耗时 = 2 分钟
MAX_WORKERS = 3
理论峰值 = 3 × (60分钟 / 2分钟) = 90 任务/小时

如果 RATE_LIMIT_MAX_TASKS=50，则实际受限于限流
如果 RATE_LIMIT_MAX_TASKS=100，则实际受限于并发
```

### 🧮 配置计算工具

```python
def calculate_optimal_config(
    total_tasks: int,           # 总任务数
    time_limit_hours: float,    # 完成时间要求（小时）
    site_limit_per_hour: int,   # 网站每小时限制
    avg_task_time_minutes: float # 平均任务耗时（分钟）
):
    """计算最优配置"""
    
    # 1. 根据网站限制确定限流配置
    rate_limit_max_tasks = int(site_limit_per_hour * 0.7)  # 70% 安全系数
    rate_limit_window_minutes = 60
    
    # 2. 计算所需并发数
    required_tasks_per_hour = total_tasks / time_limit_hours
    required_workers = required_tasks_per_hour * (avg_task_time_minutes / 60)
    
    # 3. 取限流和并发的最小值
    max_workers = min(
        int(required_workers) + 1,  # 向上取整
        rate_limit_max_tasks // 10,  # 不超过限流的 1/10
        10  # 最大不超过 10
    )
    
    return {
        "MAX_WORKERS": max_workers,
        "RATE_LIMIT_ENABLED": True,
        "RATE_LIMIT_WINDOW_MINUTES": rate_limit_window_minutes,
        "RATE_LIMIT_MAX_TASKS": rate_limit_max_tasks,
        "estimated_completion_hours": total_tasks / min(required_tasks_per_hour, rate_limit_max_tasks)
    }

# 示例使用
config = calculate_optimal_config(
    total_tasks=1000,           # 1000 个任务
    time_limit_hours=24,        # 24 小时内完成
    site_limit_per_hour=100,    # 网站限制每小时 100 次
    avg_task_time_minutes=2     # 每个任务平均 2 分钟
)
print(config)
# 输出: {
#     "MAX_WORKERS": 3,
#     "RATE_LIMIT_ENABLED": True,
#     "RATE_LIMIT_WINDOW_MINUTES": 60,
#     "RATE_LIMIT_MAX_TASKS": 70,
#     "estimated_completion_hours": 14.3
# }
```

### 案例 1: 小规模测试采集

MAX_WORKERS=2

- 并发较低，便于调试观察

### 案例 2: 国家医保局注册证号查询

**需求**：
- 采集 1000 条注册证号信息
- 目标：https://code.nhsa.gov.cn
- 网站特点：政府网站，可能有反爬限制

**分析**：
```
1. 单个任务耗时: 约 30-60 秒（查询+提取+详情）
2. 网站观察: 无明确限流提示，但建议保守策略
3. 时间要求: 24 小时内完成
```

**推荐配置**：
```bash
# 并发控制
MAX_WORKERS=3                      # 3 个任务同时运行
WORKER_MEMORY_LIMIT_MB=512

# 限流控制
RATE_LIMIT_ENABLED=true
RATE_LIMIT_WINDOW_MINUTES=60       # 1 小时窗口
RATE_LIMIT_MAX_TASKS=100           # 每小时最多 100 个任务
RATE_LIMIT_PER_CONFIG=false        # 全局限流

# 智能重试
RETRY_MIN_WAIT_MINUTES=120         # 失败后等待 2 小时再重试
RETRY_SKIP_IF_PENDING_OVER=50      # pending 超过 50 个时跳过重试
RETRY_RESPECT_RATE_LIMIT=true      # 重试时遵守限流
```

**预期效果**：
```
并发: 3 个任务同时运行
限流: 每小时最多 100 个任务
实际速率: 受限于限流，约 100 任务/小时
完成时间: 1000 任务 ÷ 100 任务/小时 = 10 小时
```

## 🛠️ 监控与调优

### 1. 查看限流状态

```bash
# API 查询
curl http://localhost:8000/api/rate-limit/status

# 返回示例
{
  "enabled": true,
  "window_minutes": 60,
  "max_tasks": 100,
  "current_count": 45,          # 当前窗口内已执行 45 个任务
  "remaining": 55,               # 还可以执行 55 个任务
  "utilization": "45/100 (45%)" # 使用率 45%
}
```

### 2. 查看进程池状态

```bash
# 通过日志观察
grep "任务分发完成" logs/app.log

# 输出示例
任务分发完成: 成功 3/5 (活跃工作进程: 3/3)
# 说明: 5 个待处理任务，成功分发 3 个，进程池已满
```

### 3. 性能指标

| 指标 | 说明 | 健康值 |
|------|------|--------|
| **限流使用率** | `current_count / max_tasks` | 60-80% |
| **进程利用率** | `活跃进程 / MAX_WORKERS` | 80-100% |
| **任务等待数** | pending 任务数量 | < 100 |
| **失败率** | `失败任务 / 总任务` | < 5% |

### 4. 调优建议

#### 限流使用率过低（< 40%）
```
问题: 限流设置过于保守，资源未充分利用
调优: 逐步提高 RATE_LIMIT_MAX_TASKS
```

#### 限流使用率过高（> 90%）
```
问题: 接近限流上限，可能触发网站反爬
调优: 降低 RATE_LIMIT_MAX_TASKS 或增加 RATE_LIMIT_WINDOW_MINUTES
```

#### 进程利用率低（< 50%）
```
问题: 
1. 限流过严，任务被频繁跳过
2. pending 任务太少
调优: 
1. 放宽限流参数
2. 增加 pending 任务
```

#### 失败率高（> 10%）
```
问题: 可能触发了网站反爬机制
调优:
1. 降低 MAX_WORKERS（减少并发）
2. 降低 RATE_LIMIT_MAX_TASKS（降低频率）
3. 增加 RETRY_MIN_WAIT_MINUTES（延长重试等待）
```

## 📌 快速决策流程图

```
开始配置
    ↓
是否有明确的网站限流？
    ├─ 是 → RATE_LIMIT_ENABLED=true
    │       └─ 根据网站限制设置 RATE_LIMIT_MAX_TASKS（× 0.7 安全系数）
    │
    └─ 否 → 是否是高风险网站（政府/金融/大厂）？
            ├─ 是 → RATE_LIMIT_ENABLED=true（保守策略）
            │       └─ RATE_LIMIT_MAX_TASKS=50-100
            │
            └─ 否 → RATE_LIMIT_ENABLED=false
                    └─ 仅通过 MAX_WORKERS 控制并发
    ↓
根据机器配置设置 MAX_WORKERS
    ├─ 低配（4核8G）→ MAX_WORKERS=2-3
    ├─ 中配（8核16G）→ MAX_WORKERS=3-5
    └─ 高配（16核32G+）→ MAX_WORKERS=5-10
    ↓
验证配置合理性
    ├─ MAX_WORKERS × 10 < RATE_LIMIT_MAX_TASKS ✅
    ├─ MAX_WORKERS × 10 > RATE_LIMIT_MAX_TASKS ⚠️ 考虑降低 MAX_WORKERS
    └─ RATE_LIMIT_ENABLED=false 且 MAX_WORKERS > 5 ⚠️ 建议启用限流
    ↓
完成配置
```

## 🎓 总结

### 记住这三点

1. **MAX_WORKERS = 同时干活的人数**
   - 控制并发，保护自己的服务器
   - 根据机器配置设置

2. **限流配置 = 对别人家的礼貌**
   - 控制频率，保护目标网站
   - 根据对方限制设置

3. **两者协同 = 既快又稳**
   - 限流优先（对外承诺）
   - 并发优化（内部提效）
   - 监控调优（持续改进）

### 推荐默认配置

```bash
# 适合大多数场景的保守配置
MAX_WORKERS=3
RATE_LIMIT_ENABLED=true
RATE_LIMIT_WINDOW_MINUTES=60
RATE_LIMIT_MAX_TASKS=100
```
